## 2. Overview

The backend exposes its behavior through **Firebase Callable Cloud Functions**. There are no raw HTTP/REST endpoints to secure, rate-limit, or document separately. The Flutter app invokes callables with the Firebase SDK; the SDK attaches the user's ID token automatically, so every call is authenticated by the platform.

**Design principle:** Firebase is the authoritative source of truth. `reserveFood` owns the entire reservation operation server-side. Client-side checks exist only for UX (fast feedback, disabled buttons, clear errors) and are never trusted for correctness.

**Endpoint inventory:**

| Endpoint | Type | Required | Purpose |
|---|---|---|---|
| `reserveFood` | Callable (`onCall`) | **Yes** | Authoritative reservation creation (the only way a reservation is ever created) |
| `releaseExpiredReservations` | Scheduled (`pubsub`) | Optional | Internal cleanup; no client contract |

## 3. `reserveFood` — Callable Function Contract

### 3.1 Invocation

| Property | Value |
|---|---|
| Name | `reserveFood` |
| Trigger | `functions.https.onCall` |
| Authentication | Required. The Firebase SDK forwards the caller's ID token. Missing/expired token → `unauthenticated`. |
| Client timeout | 10 seconds recommended |

### 3.2 Request payload

```json
{
  "foodId": "string"   // required, non-empty document ID of the food to reserve
}
```

The client sends **only** `foodId`. No other field is read. The client never supplies an OTP, a reservation ID, a deadline, a status, or any other field.

### 3.3 Success response

```json
{
  "reservationId": "string",
  "foodId": "string",
  "donorId": "string",
  "receiverId": "string",
  "reservedAt": "string",          // ISO-8601, server time
  "pickupDeadline": "string",      // ISO-8601, reservedAt + 30 minutes
  "status": "active",
  "otpVerified": false,
  "otp": "string"                  // 6 digits, generated by the server
}
```

Notes:

- `reservedAt` and `pickupDeadline` come from the **server clock**, never the device clock.
- The OTP is generated server-side. It is returned here and is also readable on the reservation document by the two participants (donor needs to show it to the receiver).
- The client should persist `reservationId` + `pickupDeadline` (or re-read the reservation document) before navigating to the Reservation Screen.

### 3.4 Error responses

The function throws `functions.https.HttpsError`; the Flutter SDK surfaces it as `FirebaseFunctionsException` whose `code` is mapped below.

| `code` | HTTP | Condition | UI message |
|---|---|---|---|
| `unauthenticated` | 401 | No token / token expired | "Please sign in again." |
| `permission-denied` | 403 | Caller role is not `receiver` | "Only receiver accounts can reserve food." |
| `permission-denied` | 403 | Caller is the donor of this food | "You can't reserve your own donation." |
| `invalid-argument` | 400 | `foodId` missing or not a string | "Select a valid food item." |
| `not-found` | 404 | Food document does not exist | "This food is no longer available." |
| `already-reserved` | 409 | `food.status != available` | "Someone just reserved this food." |
| `expired` | 410 | `food.expiryAt <= server now` | "This food has expired." |
| `unavailable` | 503 | Firebase/network unavailable | "No connection. Please try again." |
| `internal` | 500 | Unexpected server error | "Something went wrong. Please try again." |

The `permission-denied` cases carry distinct `message` strings so the client can differentiate "wrong role" from "own food" without depending on a single code.

### 3.5 Guarantees

1. **Atomicity / no partial data.** The entire operation runs inside one server-side Firestore transaction. If any validation fails, the transaction aborts and nothing is persisted — no reservation, no food change, no log.
2. **Server time.** `reservedAt = now` (server); `pickupDeadline = reservedAt + 30 minutes` (server).
3. **Server-generated OTP.** Never accepted from the client.
4. **Race safety.** Two simultaneous calls for the same food: exactly one succeeds; the loser receives `already-reserved`.
5. **Retry semantics.** A retry after a successful call fails with `already-reserved`. If the client already holds the returned `reservationId`, it may treat that as confirmation rather than an error.

### 3.6 Server-side flow (execution order)

```text
1.  Authenticate the caller (request.auth required)
2.  Load the caller's users/{uid} doc; require role == 'receiver'
3.  Validate foodId (non-empty string)
4.  BEGIN Firestore transaction
5.    Read foods/{foodId}
6.    If missing                          -> not-found
7.    If status != 'available'            -> already-reserved
8.    If expiryAt <= server now            -> expired
9.    If donorId == caller uid            -> permission-denied (own food)
10.   otp        = server-generated 6-digit code
11.   reservedAt = server now
12.   deadline   = reservedAt + 30 minutes
13.   Create reservations/{reservationId} (status 'active', otp, otpVerified false)
14.   Update foods/{foodId}  (status 'reserved', currentReservationId)
15.   Write pickup_log (action RESERVED)
16. COMMIT  (or ABORT on any step 6-9 failure)
17. Return reservation details (3.3)
```

## 4. Client Contract (Flutter)

### 4.1 Calling `reserveFood`

```dart
final callable = FirebaseFunctions.instance.httpsCallable('reserveFood');

try {
  final res = await callable.call<Map<String, dynamic>>({'foodId': foodId});
  final reservation = Reservation.fromJson(res.data);
  // navigate to ReservationScreen(reservation)
} on FirebaseFunctionsException catch (e) {
  // map e.code to the UI message in 3.4
  showReservationError(mapReserveError(e.code));
}
```

### 4.2 What the client must NEVER do (enforced server-side + by rules)

| Prohibited operation | Enforcement |
|---|---|
| Write `food.status = 'reserved'` or set `currentReservationId` | Denied by Firestore rules (no client path exists) |
| Create or delete reservation documents | `allow create: if false` on `reservations` in rules |
| Generate the OTP | Server-only; there is no write path for it |
| Decide `reservedAt` / `pickupDeadline` | Server-only; values come from the function response |
| Read reservations it is not part of | Denied by rules (participant-only reads) |

### 4.3 What the client MAY do

- Read `foods` (feed, details).
- Read reservations where the user is donor or receiver (to render the Reservation Screen and show the OTP to the receiver).
- Update its own `users/{uid}` profile (role/email/verification immutable).
- Donor: create own food, edit own food content, complete Drop & Done after OTP, release timed-out reservations.
- Receiver: cancel an active reservation, verify the OTP (client-side comparison, deadline enforced by rules via `request.time`), release timed-out reservations.
- Write `pickup_logs` for its own lifecycle actions.

### 4.4 Client-side validation (UX only, not authoritative)

- The Reserve button is enabled only when the local food view shows `status == available` and `expiryAt > now`.
- UX pre-checks give instant feedback, but the app must always await the `reserveFood` result and reconcile UI with the actual server response (the food may have been reserved or expired in the meantime).
- Network errors must not be shown as success (SR-EC-010); the reservation state is only confirmed after the callable returns.

## 5. Internal Function: `releaseExpiredReservations`

- Scheduled `every 1 minutes` (Pub/Sub). No public contract, no client caller.
- Finds `reservations` where `status == 'active' && pickupDeadline <= now` (requires composite index #9) and, per reservation, atomically: marks it `expired`, releases the food to `available` (or `expired` if food expiry has passed), clears `currentReservationId`, and writes pickup logs.
- Uses the Admin SDK (bypasses client rules; writes only the transitions defined in the architecture document section 7.3).
- Optional for MVP correctness (the app reconciles on load) but recommended for a clean demo database.

## 6. Versioning and Deployment

| Concern | Policy |
|---|---|
| Naming | Public callable keeps a stable name (`reserveFood`). Breaking request/response changes create a new function name (`reserveFoodV2`) rather than mutating the existing contract. |
| Request/response compatibility | The client and function are versioned together in the demo; schema drift is caught in emulator integration tests. |
| Deploy | `firebase deploy --only functions` for the callables. Rules deploy separately (`firebase deploy --only firestore:rules`). |
| Contract tests | The rules test suite must assert that direct reservation creation is DENIED (section 9.3 of the architecture doc) and that `reserveFood` succeeds/fails per the matrix in 3.4. |
